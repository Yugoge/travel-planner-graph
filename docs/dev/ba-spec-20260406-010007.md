# BA Specification: Fix deploy-travel-plans.sh Branch Detection

**Request ID**: dev-20260406-010007
**Created**: 2026-04-06T01:00:07Z

## Goal

Verify and fix the branch detection and clone/push flow in `scripts/deploy-travel-plans.sh` so that it correctly handles both existing (`gh-pages`) and new (empty) repositories without any hardcoded branch assumptions.

## Context

The script deploys generated travel plan HTML to a GitHub Pages repository. A prior bug had the script calling `git push origin main` (hardcoded), which failed because the deploy target repo uses a `gh-pages` branch. Commit `41e4544` and `d04e3eb` progressively fixed this to use the parameterized `$BRANCH` variable. The current code at line 541 correctly calls `git push origin "$BRANCH"`.

The remaining risk is in the **clone/init path** (Step 4, lines 348-379): the script branches on whether the remote `$BRANCH` exists, then either clones it or runs `git init` + `git checkout -b "$BRANCH"`. After analysis, two edge cases exist:

1. After a successful clone (line 354), `cd "$DEPLOY_DIR"` is NOT called within the if-branch. The script relies on the bare `cd "$DEPLOY_DIR"` at line 381. This works only if the clone exits cleanly -- if the clone fails partway through, `set -euo pipefail` exits before line 381, and the cleanup trap fires correctly. This path is safe.

2. After `git init` + `git checkout -b "$BRANCH"` in the else-branch (lines 369-371), the local repo has no remote set yet. The remote is added at line 537 (`git remote add origin "$REPO_URL"`). This is correct for a fresh init. For the clone case, `git clone` already sets `origin`, so the `git remote set-url origin "$REPO_URL"` fallback on line 537 re-asserts the correct URL. This is safe and idempotent.

3. The `git push origin "$BRANCH"` on line 541 correctly uses the parameterized branch variable. No hardcoded `main` or `master` remains in the push path.

4. The GitHub Pages API call (line 558) and GitHub CLI call (line 573) both pass `$BRANCH` dynamically. Correct.

**Conclusion**: The push flow is correct. One remaining issue: the `git commit` at line 529 will fail with "nothing to commit" if the file being deployed is identical to what was previously deployed (same content, same path). This is not caught and would cause the script to exit (due to `set -e`), skipping the push entirely without a clear error message.

## Requirements (MoSCoW)

### Must Have
- Verify no hardcoded `main` or `master` branch references remain in the clone/push path
- Handle the case where `git commit` would fail because there are no changes (idempotent deploy of same file)
- Ensure `git config user.name/email` is called before `git add` (currently it is called after -- at line 523, after `cd "$DEPLOY_DIR"` at line 381 but before `git add` at line 526, so order is correct)

### Should Have
- Clear error messaging when the deploy branch does not match any remote branch (currently handled by the `git ls-remote` check)
- `--force-with-lease` or equivalent safety for push when overwriting a stale branch state (currently uses plain push, which will fail on non-fast-forward; this is actually safe behavior)

### Could Have
- Auto-detection of the remote's default branch for new repos (currently always creates `$BRANCH`, defaulting to `gh-pages`)

### Won't Have (Non-Goals)
- Changing the source repo (travel-planner) branch detection -- the script never pushes to or pulls from the source repo's branch
- Supporting multiple simultaneous deploy branches
- Rewriting the authentication flow

## Edge Cases and Risks

- `git commit` fails with "nothing to commit" when deploying the same file twice; `set -euo pipefail` will cause script to exit at that point, skipping the push step silently from a user perspective (the local deploy in Step 6.5 already succeeded)
- `git ls-remote --heads` can be slow or fail on network timeout; currently no timeout is set
- If the clone succeeds but the repo has the branch under a different name (e.g., `pages` instead of `gh-pages`), the ls-remote check will miss it and create a new orphan branch instead of cloning, resulting in a push that creates a parallel branch rather than updating the Pages source

## Acceptance Criteria

### AC1: No hardcoded branch names in push path
- GIVEN the script is executed with default env vars
- WHEN it reaches the `git push` command
- THEN it pushes to `$BRANCH` (default: `gh-pages`), not to any hardcoded branch name

### AC2: Idempotent deploy handles "nothing to commit"
- GIVEN the same HTML file was already deployed to the gh-pages repo
- WHEN the script runs again with the same file
- THEN `git commit` is skipped gracefully (not a fatal error) and local deploy still reports success

### AC3: Fresh repo path works without remote branch
- GIVEN the GitHub Pages repo exists but has no `gh-pages` branch yet
- WHEN the script runs
- THEN it creates the branch via `git init` + `git checkout -b "$BRANCH"`, commits, and pushes successfully

## Technical Hints

- Affected file: `scripts/deploy-travel-plans.sh`
- Key lines: 348-381 (clone/init), 523-547 (commit/push), 554-588 (Pages API)
- Fix for AC2: wrap `git commit` in a conditional: `git diff --cached --quiet || git commit -m "..."`
- The `git add -A` at line 526 stages everything including the `README.md` and `index.html` updates, so the commit will usually have changes; the idempotent case only arises if the exact same file and index content are regenerated
- Root cause of original bug (`git push origin main`): was introduced before commit `41e4544`, already fixed; current version uses `$BRANCH` throughout
