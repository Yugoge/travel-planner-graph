## Edge Cases & Risks

- **R1.** **Bootstrap deadlock on fresh host.** With both arch-prop-2 (no stamp → exit 78) and arch-prop-3 (no env var → exit 78) in place, a brand-new host has a chicken-and-egg risk: the operator can't `npm install -g rednote-mcp` to seed `/usr/lib/node_modules/rednote-mcp/` (preinstall refuses), and even if they manually `cp -r /root/rednote-mcp/* /usr/lib/.../`, the launch refuses (no stamp). Mitigation: per architect `ordering_hazard_analysis.fresh_host_bootstrap`, the operator MUST do `REDNOTE_DEPLOY_OK=1 npm install` (in source for dev deps), then `REDNOTE_DEPLOY_OK=1 npm install -g /root/rednote-mcp/` (one-time seed of install path; preinstall passes because env var is set), then `scripts/deploy-to-usrlib.sh` (writes the stamp). S3 documents this in CLAUDE.md.
- **R2.** **First-run-after-this-cycle race.** This cycle adds the drift check to cli.js but the `/usr/lib/.../dist/.deploy-stamp` file doesn't exist YET (it's written by the new deploy step f). Therefore the FIRST `rednote-mcp --stdio` invocation between "deployed cli.js change" and "ran deploy-to-usrlib.sh once" would exit 78 (no stamp). Mitigation: the cycle's M8 mandates running the deploy script ONCE at the end (not at the start), so by cycle close the stamp is in place. Dev MUST follow this order: (1) write source files; (2) run deploy script once (writes stamp); (3) verify launch succeeds. NOT (1) write source; (2) trigger any rednote-mcp invocation; (3) run deploy. The order is explicit in Acceptance Criteria.
- **R3.** **`patchright` and `playwright` heavy dependencies in node_modules.** Architect's `--exclude=node_modules` flag means the deploy script does NOT propagate node_modules. The install path's existing node_modules is preserved. This is correct (architect's `exclusion_list_rationale.node_modules` confirms). Risk: if the install path's node_modules were ever wiped (e.g., by `rm -rf` or by an `npm install` that resets), the operator must re-run `REDNOTE_DEPLOY_OK=1 npm install --prefix /usr/lib/node_modules/rednote-mcp` to restore. Out-of-scope per architect; document in S3 CLAUDE.md note.
- **R4.** **Stamp module circular self-trust.** The stamp's `files` map lists `dist/utils/deployStampCheck.js`'s OWN sha256. An attacker who can rewrite `deployStampCheck.js` could no-op the check AND simultaneously update the stamp to match. Acceptable per architect `ordering_hazard_analysis.stamp_predates_drift_check_module_itself`: anyone who can write `deployStampCheck.js` can equally write `cli.js` to skip calling it; both require write access to `/usr/lib/node_modules/rednote-mcp/dist/`, which is the very thing the launch-time check is designed to detect AT NEXT START. The check trades "detects edits between deploys" for "cannot detect an edit that ALSO updated the stamp", which only a sanctioned deploy run can do. Documented; no mitigation required.
- **R5.** **`dist/auth/cookies.json` is mutated at runtime.** Architect's `what_is_in_the_files_map_exactly.exclusions` mandates excluding it from the stamp's `files` map (else every post-login launch fails). Dev MUST implement the exclusion in `deployStampCheck.js`'s walk + in deploy step f's stamp computation. Verified by AC: `grep -c "cookies\.json" /root/rednote-mcp/dist/utils/deployStampCheck.js` MUST return `>= 1` (proving the exclusion is wired).
- **R6.** **MCP transport corruption from drift-check stdout.** rednote-mcp's `--stdio` mode communicates over stdout via JSON-RPC frames. Architect's `failure_mode.do_not_log_to_stdout` is non-negotiable: ALL `deployStampCheck.js` output (success silence + drift error message) goes to stderr ONLY. Dev MUST verify by running the new module in `--stdio` mode and confirming stdout receives only valid JSON-RPC frames. AC verifies via grep of the source: NO `console.log` or `process.stdout.write` calls in `deployStampCheck.js`.
- **R7.** **`engines.node` is `>=16` (per package.json line 64).** Node builtins `fs`, `path`, `crypto` are stable across all supported versions. `crypto.createHash('sha256')` exists since Node 0.10. No version-related risk.
- **R8.** **Inline `node -e` preinstall script length.** The literal preinstall script is a long single line (~440 characters). package.json JSON encoding handles long lines fine; npm script execution handles them fine. Verified via architect's `arch-prop-3-prescription.implementation_prescription.exact_script_text` (which gives the literal text). Dev MUST copy verbatim with double-quote escaping intact (the message contains apostrophes and the inline script uses single-quoted JS string literals).
- **R9.** **Operator running `npm install` in `/root/rednote-mcp` for dev work.** Per architect, this is EXPECTED workflow and trips the guard ON PURPOSE. Mitigation is the operator setting `REDNOTE_DEPLOY_OK=1` in their interactive shell. The friction is intentional — anyone running `npm install` must consciously assert authorization. Documented in CLAUDE.md (S3).
- **R10.** **`grep` count assertions on skill.md after edits.** The skill.md edit is multi-passage (5+ distinct passages updated for internal consistency). AC verifies via grep counts (search_notes_light count >= some threshold) rather than line-by-line diff. Risk: dev makes a partial edit that passes the grep count but leaves the doc internally inconsistent (e.g., updates the catalog count to 5 but doesn't update the enumeration). Mitigation: AC enforces multiple INDEPENDENT grep counts (catalog count line, enumeration list, available-scripts block, integration-with-agents block) to make a partial edit fail at least one assertion. See AC3.
- **R11.** **Item #9 `mcp_client.py` deferral risk.** The bug (line 150 only takes content[0]; affects multi-block MCP responses) does NOT affect the current `search_notes_light` use case (the new tool returns a single content block per architect verification).
