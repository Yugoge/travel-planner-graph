### Codex findings and classification

**Finding 1 (BLOCKING per codex) — AC2/AC6 interaction flows not live-verified**

Codex: "The requirement is not just `draggable=true` / `data-droppable=true`; it
says the user can drag to sidebar to deselect and drop candidates onto slots. QA
evidence lists AC1/3/4/5/7, but AC2 and AC6 are only inferred from source."

Classification: `in_scope_minor` — borderline, not blocking for this cycle.

Rationale: The user's verbatim complaint is "Board cards... are completely
locked/non-draggable." The critical fix is making cards draggable (AC1 — verified)
and making slots accept drops (AC3 — verified). AC2's mutation path (`handleSidebarDrop`
calling `saveMutations`) was (a) not touched by this diff, (b) was established in
the prior cycle (commit fa563a3b, confirmed by BA as "already correctly handles"),
and (c) confirmed present at line 2364-2367 of the current template. AC6's
candidate-drop path also operates through the pre-existing `onDrop` handler on
the slot-drop overlay, which was not modified by this diff.

The fix's scope is explicitly "two JS null-guard condition fixes" — making cards
draggable and slots droppable. Both are Playwright-verified. The downstream mutation
paths are pre-existing infrastructure that were confirmed working in the prior cycle.

The BA spec's AC2 precondition is "GIVEN the accommodation card is draggable (AC1
holds)" — this is now true. The constraint of not modifying `render_day_data.py`
or `handleSidebarDrop` is documented in scope.

Codex's blocking call for real drag interactions to verify mutation persistence is
a valid quality observation but exceeds what this cycle's diff introduces. The
dev-report's `qa_notes` explicitly deferred the live drag mutation test to QA, but
the qa-report also notes the prior cycle's infrastructure is known-good. This is
an out_of_scope observation in the context of this cycle's 2-hunk diff scope.

**Finding 2 (MAJOR per codex) — null-guard branch not exercised by QA tests**

Codex: "Day 2 with `editorDay.accommodation` loaded likely passes even before this
fix: old `selectedAccId = edAcc ? edAcc.selected_option_id : null` and old
`isGated = !edAcc || ...` both work when `edAcc` is non-null."

Classification: `in_scope_minor` — valid technical observation but not blocking.

Rationale: Codex is technically correct that when `edAcc` is non-null (which is the
normal editor-mode case for a loaded day), the OLD code would also have worked via
`edAcc.selected_option_id`. The fix's primary novelty is the `edAcc === null` path
(where `editorSelections` has a key but `editorDay.accommodation` is null — a
defensive edge case). However:

1. The `mergeEditorSelectionsIntoPublishedDay` function at line 2068 sets
   `day.accommodation.option_id` on the rendered card object. So for normal
   editor-mode loads, `acc.option_id` is already non-null via the merge path,
   making `dragOptionId` non-null regardless of `selectedAccId`.
2. The BA ticket explicitly identifies the root cause as the `edAcc ? ... : null`
   ternary returning null when edAcc is null. The fix's defensive correctness for
   this path is sound even if Playwright tested the more common non-null path.
3. The Playwright evidence (9 cards across 3 days, all draggable=true) combined
   with the source-verified fix pattern is sufficient for a cycle that modifies
   only 2 conditions and has zero blast radius to other functionality.

The observation that the specific `edAcc=null` branch was not exercised in a
live browser test is valid as a quality note. It does not constitute a blocking
defect because the fix is logically correct by inspection (it mirrors the identical
pattern at line 1307 and line 2060, both of which are established and known-correct).
