# BA Specification: Image Fetch Failure Visibility in generate-and-deploy Pipeline

**Request ID**: dev-20260406-010005
**Created**: 2026-04-06T01:00:05Z

## Goal

Make image fetch failures visible and loud in the generate-and-deploy pipeline instead of silently swallowing them. Add a single retry on failure; if the retry also fails, emit a clearly visible warning and continue (images are optional, but the degradation must be observable).

## Context

`scripts/generate-and-deploy.sh` runs a five-step pipeline: fetch images, generate HTML, validate HTML, deploy to GitHub Pages, and print the summary URL. Step 1 (lines 80-106) calls `fetch-images-batch.py` in three separate code paths, each using `|| echo "..."` or `|| echo -e "..."` to silently absorb the exit code. As a result, a completely broken image fetch produces no distinguishable output in the pipeline log and the deploy proceeds without images -- the operator has no way to know the output is degraded until they manually inspect the deployed page.

The pattern was introduced early in the script's history and has never been revisited. The script uses `set -euo pipefail`, which means a bare invocation of `fetch-images-batch.py` that exits non-zero would already abort the pipeline; the `|| ...` constructs are intentional bypasses of that behavior.

## Requirements (MoSCoW)

### Must Have
- On any `fetch-images-batch.py` invocation that exits non-zero, automatically retry once before deciding the fetch has failed.
- If the retry also fails, print a clearly distinguishable warning (distinct from the existing yellow `⚠` informational messages -- use RED or a multi-line banner) so the failure is unmissable in CI/CD logs.
- After the loud warning, the pipeline must NOT abort -- it must continue to HTML generation and deployment (images remain optional).
- All three `fetch-images-batch.py` call sites in Step 1 must apply the same retry-and-warn logic. No call site may silently swallow failure.

### Should Have
- The retry and warn logic extracted into a single reusable bash function (e.g., `fetch_images_with_retry`) to avoid copy-paste across the three call sites.
- Print the specific exit code that was returned so operators can triage quickly.

### Could Have
- A short sleep (1-2 seconds) between the first attempt and the retry to avoid hammering a temporarily unavailable API endpoint.

### Won't Have (Non-Goals)
- Changing the retry count beyond one retry (two total attempts).
- Blocking the deploy on image failure (images remain optional).
- Modifying `fetch-images-batch.py` itself.
- Adding retry logic to any other step in the pipeline.
- Changing the threshold logic (POI_COUNT > 50) that decides whether to re-fetch.

## Edge Cases and Risks

- `2>/dev/null` is used on all current call sites to suppress Python tracebacks. The retry-and-warn approach should preserve stderr suppression on the first attempt but consider surfacing stderr on the retry failure so the operator knows the underlying error.
- The three call sites differ slightly: two pass `$FETCH_FORCE` and `$FETCH_DAY_FILTER`; one (the default no-cache, no-force path on line 104) passes hardcoded concurrency `300`. The helper function must forward all arguments faithfully.
- The script uses `set -euo pipefail`. The helper function must use `|| true` or capture the exit code explicitly -- not a bare `if` -- to prevent a retry failure from propagating as an unhandled error before the loud warning is emitted.

## Acceptance Criteria

### AC1: Retry on first failure
- GIVEN the pipeline is run and `fetch-images-batch.py` exits non-zero on the first attempt
- WHEN the Step 1 fetch logic runs
- THEN `fetch-images-batch.py` is invoked a second time with identical arguments before any failure handling occurs

### AC2: Loud warning on double failure
- GIVEN `fetch-images-batch.py` fails on both the first attempt and the retry
- WHEN the Step 1 fetch logic evaluates the result
- THEN a visually distinct multi-line warning (RED color or equivalent banner) is printed that makes the failure unmissable in a terminal or CI log; the word "FAILED" or "WARNING" must appear in the output

### AC3: Pipeline continues after double failure
- GIVEN the double-failure warning has been printed
- WHEN the pipeline proceeds
- THEN Steps 2-5 (HTML generation, validation, deploy, summary) all run to completion without error

### AC4: Silent success unchanged
- GIVEN `fetch-images-batch.py` exits zero on the first attempt
- WHEN Step 1 completes
- THEN no retry occurs and no warning is printed; behavior is identical to the current script

### AC5: All three call sites covered
- GIVEN any of the three `fetch-images-batch.py` invocations in Step 1 (lines 93, 101, 104) fail
- WHEN Step 1 runs
- THEN the retry-and-warn logic is applied consistently to each site; no call site silently ignores failure

## Technical Hints

- Affected file: `scripts/generate-and-deploy.sh` only
- The three call sites are at lines 93, 101, and 104
- Existing color variables (`RED`, `YELLOW`, `GREEN`, `NC`) are already defined at the top of the script
- A bash helper function placed before the Step 1 block keeps the diff minimal and is consistent with the script's existing style
- `set -euo pipefail` is active; use `local exit_code=0; <cmd> || exit_code=$?` to capture without triggering pipefail
