# BA Specification: Structured Brand Array in Shopping JSON

**Request ID**: dev-20260406-020002
**Created**: 2026-04-06T02:00:02Z

## Goal

Move individual brand store data from free-text `notes_base` fields in `shopping.json` into a structured `brands` array on each shopping item, eliminating the fragile regex parse in the HTML generator and giving the shopping agent direct control over brand-level data.

## Context

Shopping items in `shopping.json` currently represent mall-level POIs. Individual brand stores within a mall are embedded in `notes_base` using a custom text protocol: `[CATEGORY] BrandName Floor -- description | BrandName2 Floor -- description`. The HTML generator (`generate-html-interactive.py`) has a 94-line function `_parse_shopping_brands()` that regex-parses this format at render time. This approach is fragile, untestable, and prevents the shopping agent from expressing brand-level metadata (floor, category, description) in a typed, validatable structure.

## Requirements (MoSCoW)

### Must Have
- Add optional `brands` array field to `shopping_item` definition in `schemas/shopping.schema.json`
- Each brand entry must include: `name` (string), `category` (string, e.g., "DESIGNER"), `floor` (string, e.g., "1F"), `description` (string), and optionally `name_local`, `description_local`
- Update shopping agent prompt (`shopping.md`) to instruct the agent to populate the `brands` array directly instead of encoding brands into `notes_base`
- Update HTML generator merge logic in `generate-html-interactive.py` to read `brands` array when present, bypassing the regex parse path
- Retain backward compatibility: when `brands` is absent, fall back to existing `_parse_shopping_brands(notes_base)` parse so existing generated plans continue to render correctly

### Should Have
- Update `plan.md` shopping-agent invocation prompt section (Step 8) to include the `brands` array format in the expected output structure example
- Keep `_parse_shopping_brands()` function in the generator but gate it behind the fallback path; do not delete it yet (backward compat)
- `notes_base` on the mall-level item should remain in the schema as optional, used for non-brand notes (hours, rating, general description)

### Could Have
- Add BDD-style validation in `plan-validate.py` to flag shopping items that still use the old `[DESIGNER]` bracket pattern in `notes_base` when a `brands` array is also present (conflicting data)

### Won't Have (Non-Goals)
- Migration of any existing `shopping.json` data files in `data/` directories (existing plans are not affected; backward compat handles them)
- Changing any other agent file formats
- Removing `notes_base` from the schema (it remains valid for non-brand notes)
- Changing timeline-agent, budget-agent, or any other agent

## Edge Cases & Risks

- A mall item may have zero brands (e.g., a standalone boutique) -- `brands` should be optional with an empty array being valid
- Brand entries have no individual cost; budget is still tracked at the mall/shopping-item level (`cost` on the parent item)
- `notes_base` on the mall item may legitimately contain non-brand text (opening hours, rating, tips) alongside brand lists -- after this change, non-brand notes stay in `notes_base`; brand data moves to `brands`
- The fallback path in the generator must not double-render brands if both `brands` array and old-format `notes_base` are present -- generator must check `brands` first and skip `_parse_shopping_brands()` when `brands` is non-empty
- `save.py` validates against `shopping.schema.json` at save time; schema must accept `brands` array before the agent can save data containing it

## Acceptance Criteria

### AC1: Schema accepts brands array
- GIVEN `shopping.schema.json` is updated with a `brands` array definition on `shopping_item`
- WHEN `save.py` validates a shopping item containing a `brands` array with typed brand objects
- THEN validation passes (exit code 0) and the file is written

### AC2: Agent produces structured brands
- GIVEN the shopping agent reads the updated `shopping.md` prompt
- WHEN it processes a mall-type shopping location
- THEN the output JSON contains a `brands` array with individual objects (name, category, floor, description) instead of brand data in `notes_base`

### AC3: Generator renders from brands array
- GIVEN a `shopping.json` with a `brands` array on a mall item
- WHEN `generate-html-interactive.py` merges shopping data
- THEN it iterates `brands` directly and does not call `_parse_shopping_brands()` for that item

### AC4: Backward compatibility preserved
- GIVEN an existing `shopping.json` that has brands encoded in `notes_base` with no `brands` field
- WHEN `generate-html-interactive.py` merges shopping data
- THEN it calls `_parse_shopping_brands(notes_base)` as fallback and renders correctly (no regression)

### AC5: plan.md invocation example updated
- GIVEN the plan.md Step 8 shopping-agent prompt section
- WHEN reviewed
- THEN it shows a `brands` array in the output format example, not the bracket-encoded `notes_base` pattern
