# BA Specification: Persist meal-slot un-gating (`skip:false`) across page reload

**Request ID**: 20260527-133618
**Task ID**: 20260527-133618
**Created**: 2026-05-28T00:00:00Z
**Revised**: 2026-05-28 (QA-rejection round 1 — resolves 2 blocking defects: schema-forbidden `meals-any` skip emit + uncovered source-slot persistence at Site C)
**Tier**: STANDARD
**Prior cycle**: 20260527-062755 (in-session React-state fix; persistence explicitly out-of-scope)

## Goal

When a user drags away a meal-slot default and places a new restaurant, the slot is un-gated in React state (prior cycle) but the change is NOT persisted: on reload the slot re-gates and the placement can be lost. Close that persistence gap by emitting the existing `skip` mutation (`{skipped:false, skipped_reason:null}`) through the existing autosave pipeline at the three un-gating/selection sites. The emit is restricted to the **three real persisted meal slots only** (`breakfast`, `lunch`, `dinner`) so no schema-invalid pseudo-slot ever reaches disk, and it covers **both the source and the target** meal slot of any move so neither side re-gates on reload. NO new field types, NO new mutation types.

## Context

Prior cycle 20260527-062755 added two React-state writes that clear `slots[X].skipped = false` so a gated (e.g. `pre-arrival`) meal slot becomes droppable in-session. Those writes never reached the backend, so `day-NN.json` still carries `skipped:true, skipped_reason:"pre-arrival"`. The server-side `skip` mutation handler already exists (`save.py` `_apply_skip_mutation`, lines 107-114) and the `slot_envelope` schema already models `skipped`/`skipped_reason` — but the front-end has **never emitted a `skip` mutation** (confirmed: zero `type:'skip'` occurrences in `react_template.tpl`). This cycle wires the existing-but-unused `skip` mutation into the un-gating/selection sites.

### Revision drivers (QA round 1)

- **Defect 1 (critical)**: the prior spec gated skip emits on `MEAL_SLOTS.has(...)`. But `MEAL_SLOTS = new Set(['breakfast','lunch','dinner','meals-any'])` (`react_template.tpl:2227`) INCLUDES `meals-any`, which is NOT a valid persisted slot key. `day.schema.json` `slots` has `additionalProperties:false` and permits only the 6 named slots (`breakfast`, `morning_activity`, `lunch`, `afternoon_activity`, `dinner`, `evening_activity`); `accommodation` is a separate top-level key. A `skip` mutation with `slot:'meals-any'` would make `save.py:_get_or_create_slot` execute `day["slots"].setdefault("meals-any", {...})` (`save.py:65`), creating a `slots['meals-any']` key on disk → schema-invalid data corruption (`additionalProperties:false` violation). Fix: a NEW restricted guard set `SKIPPABLE_MEAL_SLOTS`.
- **Defect 2 (major)**: Site C `board` branch emits `select(sourceSlotId, null) + select(toSlotId, optionId)`. The prior spec only un-gated `toSlotId`. If the SOURCE slot is a skipped real meal slot, moving its item away leaves it `skipped:true` on disk → re-gates on reload (same bug as Site A, on the source side). Fix: symmetric source+target skip coverage at every site, de-duplicated.
- **Codex round-2 finding (in-scope, same defect class)**: the `direction === 'board'` direct-`saveMutations` move handler is NOT unique to line 1915 — it is **duplicated across 6 drop handlers** in the file (`react_template.tpl:917`, `994`, `1072`, `1150`, `1307`, `1915`), one per board surface (KanbanView meals row `917`, cafe `994`, activity `1072`, entertainment `1150`, accommodation `1307`, and TimelineView `1915`). Each has the identical `board`/`candidates`/`else` triad. Two of them target real meal slots (`917` = meals row, `1915` = timeline slot which can be a meal). The prior spec claimed Site C was "the complete set" — it was not. Fix: apply the `buildSkipMuts` coverage to ALL SIX board-drop handlers uniformly. Because `buildSkipMuts` filters by `SKIPPABLE_MEAL_SLOTS`, the activity (`994`/`1072`/`1150`) and accommodation (`1307`) handlers become schema-safe no-ops (no skip emitted), while the meal handlers (`917`, `1915`) un-gate both source and target. (QA had counted `.skipped=` WRITES, of which there are exactly 2; these 6 handlers do NOT write `.skipped` — they are `select`-only emit paths, the same category as the original Site C — so they were outside QA's count but inside the emit-site set.)

## Valid persisted meal slots (verbatim from `day.schema.json`)

`schemas/v2/day.schema.json` lines 53-66 define `slots`:

```json
"slots": {
  "type": "object",
  "properties": {
    "breakfast": {"$ref": ".../slot_envelope"},
    "morning_activity": {"$ref": ".../slot_envelope"},
    "lunch": {"$ref": ".../slot_envelope"},
    "afternoon_activity": {"$ref": ".../slot_envelope"},
    "dinner": {"$ref": ".../slot_envelope"},
    "evening_activity": {"$ref": ".../slot_envelope"}
  },
  "required": ["breakfast", "morning_activity", "lunch", "afternoon_activity", "dinner", "evening_activity"],
  "additionalProperties": false
}
```

- The **only valid persisted MEAL slots** are: **`breakfast`, `lunch`, `dinner`**.
- `meals-any` is NOT a valid persisted slot key — it is a UI-only pseudo-slot present in the front-end `MEAL_SLOTS` set but absent from the schema. Persisting it (via a skip or any other mutation) triggers `additionalProperties:false` violation.
- `accommodation` is a separate top-level day key, not under `slots`, and is never a meal slot.

Therefore the skip-emit guard set is exactly: `SKIPPABLE_MEAL_SLOTS = new Set(['breakfast', 'lunch', 'dinner'])`.

## Reference Source (Contract C)

- **Tier**: tier_2_verified (server handler + both schemas verified this session by Read)
- **Source**: `scripts/lib/server/save.py:107-114` (`_apply_skip_mutation`), `save.py:57-65` (`_get_or_create_slot`), `schemas/v2/day.schema.json:53-66` (slot key allow-list), `schemas/v2/poi-common.schema.json` (`slot_envelope` `skipped`/`skipped_reason`).
- **`_apply_skip_mutation` reads** (verbatim): `slot_id = mut.get("slot")`; `if not slot_id: return`; `slot = _get_or_create_slot(day, slot_id)`; `extra = mut.get("extra") or {}`; `slot["skipped"] = bool(extra.get("skipped", True))`; `slot["skipped_reason"] = extra.get("skipped_reason")`.
- **Therefore the canonical `skip` payload is**: `{ type: 'skip', slot: '<slotId>', extra: { skipped: false, skipped_reason: null } }`.
  - NOTE the field name is **`slot`** (not `slot_id`) at the mutation top level — `_apply_skip_mutation` calls `mut.get("slot")`. This mirrors how `select` mutations name the field (`select` also uses `slot:` — see `react_template.tpl:2406,2436,2945,2989`).
- **`_get_or_create_slot` creates whatever slot_id it is given** (`save.py:65` `day["slots"].setdefault(slot_id, ...)`). It does NOT validate against the schema. The schema's `additionalProperties:false` is enforced only at validate-time, not save-time. So a skip emit with an invalid `slot` (e.g. `meals-any`) silently writes a forbidden key to disk. **The front-end is the only guard against this; it MUST restrict skip emits to `SKIPPABLE_MEAL_SLOTS`.**
- **`skipped_reason: null`** is schema-valid: enum includes `null`, and the validator only rejects `skipped_reason:null` when `skipped=true`. Since `skipped=false`, `null` reason is correct.
- **Copy allowed**: yes — copy the payload shape from the server handler contract; copy the valid-slot-key list verbatim from `day.schema.json`.
- **Dev constraint**: There are ZERO existing front-end `skip` emit sites to mirror. Ground the payload shape strictly on `_apply_skip_mutation` (tier_2) — do NOT invent extra fields. Mirror the top-level `slot:` field-naming convention from the existing `select` emit sites. Gate every skip emit on `SKIPPABLE_MEAL_SLOTS.has(slotId)` (the 3 real meal slots) — NEVER on `MEAL_SLOTS.has(slotId)` (which admits `meals-any`).

## Edge Cases & Risks

- **`meals-any` data corruption (QA Defect 1 — RESOLVED)**: gating skip emits on `MEAL_SLOTS` (which contains `meals-any`) would let a `skip` mutation with `slot:'meals-any'` reach `save.py`, where `_get_or_create_slot` (line 65) would `setdefault('meals-any', {...})` under `day["slots"]`, producing a key the `day.schema.json` `additionalProperties:false` rule forbids → schema-invalid file. Resolution: the new `SKIPPABLE_MEAL_SLOTS` set ({breakfast, lunch, dinner}) excludes `meals-any`, so no skip emit can ever carry it. AC7 enforces this.
- **Source-slot re-gate at Site C board branch (QA Defect 2 — RESOLVED)**: the board move emits `select(sourceSlotId, null)` — emptying the source. If `sourceSlotId` is a skipped meal slot, it stays `skipped:true` on disk and re-gates on reload. Resolution: Site C `board` branch now emits `skip(false)` for BOTH `sourceSlotId` and `toSlotId` (each `SKIPPABLE_MEAL_SLOTS`-gated). Mirror at Site B for the `originSlotId` move case. AC2b covers this.
- **De-duplication**: if a move's source and target are the same slot (degenerate self-drop), the de-dup guard collapses to a single skip mutation. Build the skip-mutation list via a `Set` of slot ids filtered by `SKIPPABLE_MEAL_SLOTS` to guarantee at most one skip per slot per batch.
- **Site A emits select(null) + skip(false)**: After un-gate-by-deselect, slot has `skipped:false` and `selected_option_id:null`. Schema-valid (null selection allowed in draft/review stages) and matches in-session React state. `options[]` synthesis is React-state-only and not persisted by `select`/`skip`; on reload the slot reads disk `options[]`. Acceptable: the un-gate (`skipped:false`) is what must persist.
- **STAGE_GATE interaction (QA-F4 / codex F2)**: if the day's `stage` is already `user-selected` or later, persisting a required meal slot as `skipped:false` with `selected_option_id:null` (the Site A / board-source deselect state) would trip `STAGE_GATE_VIOLATION` in `scripts/lib/trip_contract/validators.py` (`_check_stage_gate`) at VALIDATION time. This is NOT a save-time concern (`save.py` does not run the stage gate on save), so it does NOT block AC3 persistence. No new gating logic this cycle ("no new logic"); documented so QA's AC5 regression pass is aware. A validation failure after deselect on approved days would be a separate cycle. The deselect is the user's explicit action; un-gate persistence is what they asked for.
- **Site B move case**: when `originSlotId` is a real meal slot and differs from target, both origin and target are un-gated. The origin is emptied (`select` moves the option out, line 2984) and must not remain gated — hence the origin skip emit. De-dup ensures origin≠target so two distinct skips at most.
- **Field-name trap**: `skip` payload top-level key is `slot` (not `slot_id`). Using `slot_id` would make `_apply_skip_mutation` no-op (`mut.get("slot")` → None → early return). Dev MUST use `slot`.
- **`extra` nesting**: `skipped`/`skipped_reason` go INSIDE `extra`, not at mutation top level. `_apply_skip_mutation` reads `mut.get("extra")`.
- **options[] persistence (codex F5)**: React-state `options[]` synthesis at Site A (lines 2352-2401) is not persisted by `skip`/`select`. The un-gate (`skipped:false`) survives reload regardless; a synthesized option absent from disk `options[]` won't reappear post-reload. For AC3's placement path (Site B), the placed option exists in disk `options[]` (sidebar candidates sourced from `options[]`), so `selected_option_id` resolves. Existing `select`-handler behavior, unchanged.

## Acceptance Criteria

### AC1 — `skip` mutation on deselect-from-skipped-slot (Site A, source)
- GIVEN `handleSidebarDrop` clears `slots[srcSlotId].skipped` in React state (line 2366) and `srcSlotId` is in `SKIPPABLE_MEAL_SLOTS`
- WHEN the deselect handler runs
- THEN the front-end also enqueues `{type:'skip', slot:'<srcSlotId>', extra:{skipped:false, skipped_reason:null}}` via `saveMutations(dayNum, [...])`, batched with the existing `select(srcSlotId, null)` emit. The skip emit is behind the `SKIPPABLE_MEAL_SLOTS.has(srcSlotId)` check, not at the unconditional 2406 `saveMutations` line.

### AC2 — `skip` mutation on applyBridge clear (Site B, target + origin)
- GIVEN `applyBridge` clears `slots[targetSlotId].skipped` in React state (line 2963) and `targetSlotId` is in `SKIPPABLE_MEAL_SLOTS`
