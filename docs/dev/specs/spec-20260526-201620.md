# BA Specification: Meal UX — 4 Bugs (cross-slot drop, image parity, airplane-meal restore, optional badge)

**Request ID**: 20260526-201620
**Created**: 2026-05-26T20:16:20Z
**Tier**: STANDARD

## Goal

Fix 4 meal-related UX bugs in `scripts/lib/react_template.tpl`:

1. AC1 — Cross-slot meal drop: a dinner card dragged to sidebar should be draggable back to ANY meal slot (breakfast/lunch/dinner), not only dinner.
2. AC2 — Image parity: images must render consistently between board cards and sidebar candidate cards.
3. AC3 — Airplane meal (PLAN_DATA-defined, `meals-any` slot) vanishes from sidebar after deselect.
4. AC4 — Board does not show the `optional` badge on 2nd+ options per meal slot.

## Evidence (Contract A)

### AC1
- **Observed**: "原先的dinner只能放回dinner" — dinner item dragged to sidebar can only return to the dinner column
- **Measured**: `handleSidebarDrop` synthesis (lines 2357-2379) only triggers `if (planItem)` where `planItem = publishedDay.meals[srcSlotId]`. Synthesis writes back to `editorTripData.slots[srcSlotId].options[]`. After a cross-slot drop (sidebar→breakfast), `applyBridge` (lines 2926-2956) moves the option from `originSlotId` to `targetSlotId` in `editorTripData` — removing it from the original slot. If the user then drags back to sidebar, the item IS in `editorTripData.slots['breakfast'].options[]`, so synthesis finds `planItem` only for the original slot (`dinner`), not for `breakfast`. The re-synthesis pushes back to `dinner.options[]` and sets `_originSlotId: 'dinner'`, so the sidebar card advertises `dinner` as its origin, and a subsequent drag only routes to `dinner`.
- **Expected**: `_originSlotId` on a re-synthesized sidebar card should reflect wherever the option currently lives, not the PLAN-default slot. After cross-slot moves, the synthesis fallback (editorDay path) must capture the option as currently living in the target slot, and the sidebar card must carry that slot as `_originSlotId`.
- **Gap**: Synthesis fallback when `planItem` is null or when the option has moved to a different slot does not correctly set `_originSlotId` to the current location.

### AC2
- **Observed**: "放到右侧和放到左侧渲染使用图片应该是一样的！" — image discrepancy between board and sidebar
- **Measured**: Board renders `opt.cover_image || opt.image` (line 882) from `effectiveDay` (publishedDay-sourced). Sidebar renders `rawOpt.cover_image || rawOpt.image` (line 2528) from `editorTripData.slots[slotId].options[]`. When `handleSidebarDrop` re-synthesizes from `planItem`, it copies only `planItem.cover_image || planItem.image` (line 2372) — losing any richer image URL the original editorTripData option carried. PLAN data also uses `image` not `cover_image`, so synthesized sidebar objects often have `cover_image: null` while board objects have `image: <url>`.
- **Expected**: Synthesized objects in `editorTripData.slots[].options[]` must carry BOTH `cover_image` and `image` fields, populated from whichever source has the image. Priority: existing editorTripData option object > planItem.
- **Gap**: Synthesis overwrites with a reduced field set; does not attempt to look up the already-existing editorTripData option before pushing a new reduced copy.

### AC3
- **Observed**: "飞机餐被放到右边之后不能再放回去了！" — airplane meal (PLAN_DATA-defined) disappears from sidebar after deselect
- **Measured**: (a) `mealSlotIds = ['breakfast', 'lunch', 'dinner']` (line 2314) does not include `'meals-any'`, so `slots['meals-any'].options[]` is never iterated in `mealsGroup` build — such items never appear in sidebar regardless of editorTripData state. (b) `handleSidebarDrop` synthesis guard (line 2357) is `if (planItem)` where `planItem = publishedDay.meals[srcSlotId]` — `publishedDay.meals['meals-any']` is null for PLAN_DATA meals in that slot, so the entire synthesis block is skipped and the option is never re-inserted into `editorTripData`.
- **Expected**: Items in `slots['meals-any'].options[]` should appear in the sidebar Meals group; deselecting a `meals-any` board card should re-add it to `editorTripData.slots['meals-any'].options[]`.
- **Gap**: Two independent omissions: `mealSlotIds` omits `'meals-any'`; synthesis fallback has no `editorDay`-based path when `planItem` is null.

### AC4
- **Observed**: "同一个时间吃饭可以加入多个餐厅，第二个及以后的都是optional！" — multiple options per meal slot, 2nd+ should show optional badge
- **Measured**: Board renders `day.meal_alternatives[type][]` at line 854-855 with `_isPrimary: false` but no `_isOptional` flag. The `cardStyle` call at line 869 is `cardStyle(catColor, opt._isPrimary)` (2 args, `isOptional` defaults undefined/falsy). No optional badge is shown. Cafe cards at line 969 and attraction cards at line 1048 use `{c.optional && <span style=...>}` pattern.
- **Expected**: Every entry in `day.meal_alternatives[type][]` should render with `optional` badge (same style as cafe/attraction) and dashed-border card style.
- **Gap**: `_isOptional` flag not set on alternatives; `cardStyle` and `hoverOff` not passed the flag; badge JSX missing.

## Edge Cases & Risks

1. **`isMealSelected` check for `meals-any`**: After adding `meals-any` to `mealSlotIds`, `isMealSelected` iterates `mealSlotIds` — must NOT include `meals-any` there because the selection key is always a concrete slot (`breakfast`/`lunch`/`dinner`). Codex finding #4 confirmed: split `mealSlotIds` (sidebar source scan) from `mealSelectionSlotIds` (selected-state check).
2. **Stale `editorDay` closure in `handleSidebarDrop`**: `handleSidebarDrop` closes over `editorDay` which is stale at call time. Use `prev` (the `setEditorTripData` updater argument) for lookup within the functional update — this is already the correct pattern for the existing code (lines 2358-2378).
3. **`_originSlotId` for items in `meals-any`**: When synthesis pushes back to `srcSlotId = 'meals-any'`, the sidebar card must set `_originSlotId: 'meals-any'`. The `applySelection`/`applyBridge` handlers already gate the copy-to-target-slot path with `originSlotId !== 'meals-any'` (line 2401), so these items will only work with `applySelection`'s direct-set path — which is correct and sufficient for in-session UX.
4. **AC4 `alts.forEach` index**: `day.meal_alternatives[type]` contains ONLY alternatives (primary is in `day.meals[type]`), so `ai === 0` is already the second restaurant. All entries at any `ai` should be `_isOptional: true`.
5. **cardStyle 3rd arg for alternatives**: `cardStyle(catColor, opt._isPrimary, opt._isOptional)` — when `_isPrimary: false` and `_isOptional: true`, both conditions apply; `isOptional` takes precedence in `cardStyle` (checked first), so dashed border renders correctly.

## Acceptance Criteria

### AC1: Cross-slot meal drop — sidebar card carries correct originSlotId

GIVEN a meal item X originally in the `dinner` slot on the board
WHEN user drags X to the sidebar (deselects it)
AND drags X from the sidebar to the `breakfast` board slot
AND drags X from the `breakfast` board slot back to the sidebar
THEN the sidebar card for X has `data-origin-slot-id="breakfast"` (the current slot, not `"dinner"`)
AND the user can drag X from sidebar to either `lunch` or `dinner` without rejection

Verification: check `data-origin-slot-id` attribute on the sidebar card element after the second board→sidebar drop.

### AC2: Image parity between board and sidebar

GIVEN a meal item with a `cover_image` URL in the original API data
WHEN the item is shown on the board (effectiveDay) AND in the sidebar candidates panel
THEN both card renders display the same image
AND the synthesized editorTripData option object has `cover_image` populated (not null) when the original editorTripData option or planItem has an image

Verification: compare `img[src]` of board meal card vs sidebar meal card for the same option_id.

### AC3: PLAN_DATA airplane meal reappears in sidebar after deselect

GIVEN a day where `editorTripData.slots['meals-any'].options[]` contains a meal item (airplane meal)
AND that item is shown as selected on the board
WHEN user drags the board card to the sidebar (deselects)
THEN the item reappears in the sidebar Meals group (is NOT lost)
AND the item can be dragged from sidebar back to any meal slot on the board

Verification: count sidebar meal group items before deselect and after — count must not decrease for this item.

### AC4: Optional badge on 2nd+ meal options on board

GIVEN a day where `day.meal_alternatives['dinner']` has at least one entry
WHEN the board Meals section renders
THEN the alternative meal card(s) display the `optional` badge with style `{ padding: '1px 4px', background: '#f5f5f3', borderRadius: '3px', fontSize: '9px', color: '#9b9a97', border: '1px solid #e0e0e0' }`
AND the card renders with dashed border style (via `cardStyle(catColor, false, true)`)
AND the primary meal card does NOT show the optional badge

Verification: check for `span` containing "Optional" / "选填" text inside `data-slot-card="alternative"` meal card.

**New**:
```js
        if (MEAL_SLOTS && MEAL_SLOTS.has(srcSlotId) && payload.optionId && setEditorTripData) {
          const planMeals = publishedDay && publishedDay.meals;
          // planItem may be null for meals-any / PLAN_DATA-defined items not in publishedDay.meals
          const planItem = planMeals && planMeals[srcSlotId];
          const optionId = payload.optionId;
          setEditorTripData(prev => {
            if (!prev || !prev.days) return prev;
            const updated = JSON.parse(JSON.stringify(prev));
            const dayEntry = updated.days.find(d => Number(d.day) === Number(dayNum));
            if (!dayEntry || !dayEntry.slots) return prev;
            if (!dayEntry.slots[srcSlotId]) dayEntry.slots[srcSlotId] = { options: [] };
            if (!dayEntry.slots[srcSlotId].options) dayEntry.slots[srcSlotId].options = [];
            const already = dayEntry.slots[srcSlotId].options.some(o => o.option_id === optionId);
            if (!already) {
              // Prefer: (1) existing v2 option from current day any slot, (2) planItem synthesis
              let srcOpt = null;
              for (const sKey of Object.keys(dayEntry.slots)) {
                const s = dayEntry.slots[sKey];
                if (!s || !s.options) continue;
                const hit = s.options.find(o => o.option_id === optionId);
                if (hit) { srcOpt = hit; break; }
              }
              if (srcOpt) {
                // Clone and re-insert into srcSlotId (AC1: correct _originSlotId will be srcSlotId)
                dayEntry.slots[srcSlotId].options.push({ ...srcOpt });
              } else if (planItem) {
                // PLAN fallback: populate both cover_image and image for parity (AC2)
                const planImg = planItem.cover_image || planItem.image || null;
                dayEntry.slots[srcSlotId].options.push({
                  option_id: optionId,
                  name: planItem.name_base || planItem.name || optionId,
                  name_local: planItem.name_local || '',
                  cost: planItem.cost || 0,
                  cover_image: planImg,
                  image: planImg,
                  notes_base: planItem.notes_base || '',
                  notes_local: planItem.notes_local || '',
                });
              }
            }
            return updated;
          });
        }
```

**Why this is correct**:
- The search iterates `dayEntry.slots` inside the `setEditorTripData` updater (uses `prev` not stale `editorDay`), avoiding stale closure.
- When the option has been moved cross-slot by `applyBridge`, it now lives in the target slot, and the loop finds it there. The clone is pushed back to `srcSlotId.options[]` — after `setEditorSelections(...null)` fires, `mealsGroup` re-builds from `slots[srcSlotId].options[]` and finds the item with `_originSlotId: srcSlotId` (correct current position).
- When `srcSlotId === 'meals-any'` and there's no planItem, the loop finds the option in `slots['meals-any'].options[]` itself (it wasn't removed yet at synthesis time) and clones it — ensuring re-insertion.
- Both `cover_image` and `image` are set in the planItem fallback path (AC2 fix for board-rendered `image` field vs sidebar `cover_image` preference).
