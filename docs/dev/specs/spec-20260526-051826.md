# BA Specification: CandidatesSidebar Visibility, Move-Semantics, and Budget Category Update

**Request ID**: 20260526-051826
**Created**: 2026-05-26T05:18:26Z

## Goal

Fix four confirmed bugs in the travel-planner React editor (`react_template.tpl`): (1+4) items removed from the board disappear from the candidates sidebar instead of reappearing as unselected options, (5) dragging a candidate to the board keeps the card in the sidebar instead of moving it, and (9) per-category budget breakdown goes stale after any plan change. Also apply a cosmetic label fix for issue 2 (restaurant type clarity).

## Context

The editor maintains two data planes: `publishedDay` (static PLAN_DATA baked at render time) and `editorTripData` (v2 API data, fetched once at load). `CandidatesSidebar` builds its displayed option list exclusively from `editorTripData.days[n].slots[slotId].options[]`. Items that live only in `publishedDay.meals` (e.g., the airplane meal placeholder, or a plan-default restaurant) are absent from `editorDay.slots[slotId].options[]` and therefore never appear in the sidebar — before or after a drag interaction. The budget display reads `effectiveDay.budget`, which is derived from static `publishedDay.budget`; the `recomputeBudget` API response carries a full per-category breakdown (`entry.breakdown`) that is currently discarded.

**QA pre-dev correction (2026-05-26)**: The original spec incorrectly identified `applySelection` (lines 2354-2381) as the fix target for Issue 5 and `entry.budget` as the budget field. Both were corrected after QA source verification — see Technical Hints and AC3/AC4 below.

## Evidence (Contract A)

### Issues 1 & 4 — Item disappears from sidebar after board removal
- **Observed**: "After removing a restaurant from board (drag to sidebar), it disappears from sidebar candidates panel. After removing airplane meal (flight day), sidebar list no longer updates — item completely gone."
- **Measured**: `mealsGroup` built at lines 2310-2322; source is `editorDay.slots[slotId].options[]` only. `handleSidebarDrop` (lines 2338-2351) sets `editorSelections[key] = null` — does NOT add item back to `options[]`. If the item was never in `options[]` (e.g., PLAN-default meal from `publishedDay.meals`), it was invisible in the sidebar before and after the drag.
- **Expected**: After a board→sidebar drag, the removed item should be visible in the sidebar as an unselected candidate.
- **Gap**: Items in `publishedDay.meals` that are absent from `editorDay.slots[slotId].options[]` are not synthesized back into `options[]` on deselect. The existing `preserveCurrentAccommodationOption` pattern (lines 2799-2832) solves this exact problem for accommodation but is absent for meals.

### Issue 5 — Sidebar card stays after drag to board
- **Observed**: "After dragging from right sidebar to left board, card STILL shows in right sidebar — should move (not copy)."
- **Measured**: `applyBridge` (lines 2869-2897) is the live runtime path for `direction='candidates'` drag-to-board. It is assigned as `window.applyEditorSelection` at line 2898 and called by `slot-drop.onDrop` via `window.applyEditorSelection(optionId, toSlotId, originSlotId)`. `applyBridge` sets `editorSelections[key]=optionId` and cross-copies the option to the target slot, but never removes the option from the source slot `options[]`. The card therefore remains visible. `applySelection` (lines 2354-2381) is DEAD CODE — it is defined but never called in the live drag path.
- **Expected**: Dropping a sidebar card onto the board should remove it from the sidebar (move semantics, not copy).
- **Gap**: `applyBridge` must additionally remove the option from `editorTripData.days[n].slots[originSlotId].options[]` via `setEditorTripData` when `originSlotId` is set and differs from `targetSlotId`.

### Issue 9 — Budget per-category breakdown stale
- **Observed**: "After changing the plan, budget doesn't update."
- **Measured**: `recomputeBudget` (lines 2684-2703) calls `/api/budget/recompute` and on success only stores `entry.day_total` into `setLiveDayTotal`. The `entry.budget` per-category object in the response is silently discarded. Budget display at lines 1378-1385 reads `day.budget[r.k]` from `effectiveDay.budget`, which traces back to static `publishedDay.budget` — unchanged after any edit.
- **Expected**: After any `saveMutations`, the per-category budget rows (meals, accommodation, transport, etc.) should reflect the recomputed values from the API.
- **Gap**: `recomputeBudget` must merge `entry.budget` into `editorTripData.days[n].budget` via `setEditorTripData`.

### Issue 2 — Restaurant type label implies slot restriction
- **Observed**: "Restaurant type cannot be locked — a restaurant is a restaurant, any restaurant should work for any meal slot."
- **Measured**: `_isCompatible` (lines 2222-2227) already treats all MEAL_SLOTS as mutually compatible — no type-filtering exists in the drag logic. Sidebar meal card type label at line 2497 renders `mealsLabel` which equals the `_originSlotId` slot name (e.g., "dinner"), making the user believe the card is restricted to that slot type.
- **Expected**: Meal cards in the sidebar should not display a slot-type label that implies restriction.
- **Gap**: Cosmetic only — replace `mealsLabel !== 'meals' ? mealsLabel : ...` with a fixed "餐厅/Restaurant" label.

## Edge Cases & Risks

- **Synthesized option shape**: When synthesizing a PLAN-default meal option back into `editorDay.slots[slotId].options[]`, the synthesized object must be structurally compatible with what `mealsGroup` expects (`option_id`, `name`, `name_local`, `cover_image`, `cost`). Use the same shape as `preserveCurrentAccommodationOption` (lines 2812-2819).
- **Move semantics — empty slot guard**: After removing an option from `options[]` in move semantics, if the target slot is the same as origin slot (same-slot reorder), the deselection must not re-remove the item after it has just been added as selected.
- **Budget merge timing**: `recomputeBudget` is called async after `saveMutations` resolves. If two saves fire in rapid succession, the sequence guard (`budgetSeqRef.current[dayNum]`) already prevents stale writes to `liveDayTotal` — the same guard must apply to the new `entry.budget` merge.
- **Flight-day airplane meal**: The airplane meal option ID may be a synthetic ID (e.g., `'flight:board-default'` style). When synthesizing back into options, the `option_id` from `publishedDay.meals.breakfast` (or whichever slot held it) must be used verbatim.

## Acceptance Criteria

### AC1: Board→sidebar drag — removed item reappears in candidates (Issues 1+4)
- GIVEN a day with at least one meal slot whose selected option originated from `publishedDay.meals` (not from `editorDay.slots[slotId].options[]`)
- WHEN the user drags the board card for that meal to the `CandidatesSidebar` (handleSidebarDrop fires, `editorSelections[key]` becomes null)
- THEN the item appears in the sidebar `mealsGroup` as an unselected card (no green border) on the next render

### AC2: Board→sidebar drag — item is synthesized with correct shape
- GIVEN `publishedDay.meals[slotId]` contains a meal item with `name`, `name_local`, `cost`, and optionally `image`
- WHEN the board→sidebar drag fires
- THEN `editorTripData.days[n].slots[slotId].options[]` contains a new entry with matching `option_id`, `name`, `name_local`, `cost`, and `cover_image` fields (nil-safe)

### AC3: Sidebar→board drag — card removed from sidebar (Issue 5)
- GIVEN a meal candidate is visible in the sidebar and not selected
- WHEN the user drags it to a board meal slot (applySelection fires with direction `'candidates'`)
- THEN the card is absent from the sidebar on the next render (option removed from `editorTripData.days[n].slots[originSlotId].options[]`)

### AC4: Per-category budget updates after plan change (Issue 9)
- GIVEN a day with per-category budget rows (meals, accommodation, etc.) displayed in the board
- WHEN the user makes any selection change (saveMutations → recomputeBudget resolves)
- THEN the budget row values displayed in the board reflect the `entry.budget` values from the `/api/budget/recompute` response, not the stale `publishedDay.budget` values

### AC5: Budget sequence guard preserved
- GIVEN two rapid save operations fire for the same day
- WHEN the second recomputeBudget response arrives after the first
- THEN only the values from the latest response (highest seq) are applied to `editorTripData.days[n].budget`

### AC6: Meal sidebar card label — neutral type display (Issue 2)
- GIVEN a meal candidate in the sidebar whose `_originSlotId` is `'dinner'` (or any specific slot)
- WHEN the sidebar renders the card type label
- THEN the label reads "餐厅" (zh) or "Restaurant" (en), not "dinner" or "breakfast" or "lunch"
