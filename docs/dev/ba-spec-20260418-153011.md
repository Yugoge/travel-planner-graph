# BA Specification: Currency System Architecture Redesign

**Request ID**: dev-20260418-153011
**Created**: 2026-04-18T15:30:11Z

## Goal

Replace the fragmented, multi-directional currency conversion architecture (CNY↔EUR via `fallback_exchange_rate` + `cross_rates_to_cny`) with a clean single-direction model: 1 EUR = X local, where EUR is the traveller's home currency and `currency_local` is the trip's local currency. This eliminates dual-source confusion, stale USD agent instructions, and the multi-hop conversion chain in the HTML generator.

## Context

The project started with an ad-hoc CNY-centric model where `fallback_exchange_rate` stored CNY→EUR (0.128), agent prompts instructed LLMs to output costs "in USD" (never collected or converted), and the HTML generator performed a multi-hop conversion: source → CNY → display. This created three incompatible currency surfaces: agent instructions said USD, the config was EUR/CNY, and data files wrote CNY. The redesign unifies everything around: (a) a single home currency (EUR), (b) a single local currency per trip (`currency_local`), and (c) a simple division `cost ÷ exchange_rates[currency_local]` for display.

## Edge Cases & Risks

- **Risk 1**: `fetch-exchange-rate.sh` is called with `EUR CNY` but the new config stores the inverse (1 EUR = 8.05 CNY). The generator must call the script as `EUR <currency_local>` and use the result directly. Verify the script's output direction matches the new formula.
- **Risk 2**: Legacy call sites at lines 1114, 1143, 1323, 1333, 1347, 1361 reference `ticket_price_eur`, `price_range_eur_low`, `cost_eur`. These fields may not exist in current data (china-20260412 data uses `cost` + `currency_local`). The generator must fall back to `cost` field gracefully.
- **Risk 3**: `_extract_transport_cost_cny` at line 211 reads `cost_cny` field — this method name implies CNY and may need renaming/refactoring as part of R5.
- **Risk 4**: budget.schema.json currently has no currency field at day level. Adding `currency_local` must maintain backward compatibility (optional field, not required).
- **Risk 5**: plan-validate.py location-currency validation (R9) requires a location → expected_currency lookup. For China trips, all locations map to CNY. The validator must use the plan-level `currency_local` as the expected value for all days unless day-level override exists.
- **Risk 6**: CORRECTED (was wrong in original spec). The costs 42, 48, 60, 44 in accommodation.json are EUR values mislabeled as CNY. Evidence: Gaodu Hotel notes say "350 CNY/night" but cost=42 (42×8.05=338 CNY); Atour Chengdu real price ~386 CNY = 48 EUR×8.05; Moxy Xi'an notes say "304 CNY/night" with cost=44 (44×8.05=354 CNY); Heishi M+ Shanghai notes say "500 CNY/night" with cost=48 (48×8.05=386 CNY). Dev MUST multiply all cost values by 8.05, per user instruction.
- **Risk 7 (OBJ-3 — Dual-field migration edge case)**: Three older trip directories use a dual-field cost schema that is incompatible with the new single-field `cost + currency_local` model: (a) `beijing-exchange-bucket-list-20260202-232405/transportation.json` uses `cost` (CNY) + `cost_usd`; (b) `china-exchange-bucket-list-2026/transportation.json` uses `cost_cny` + `cost_eur` (no `cost` field); (c) `china-feb-15-mar-7-2026-20260202-195429/transportation.json` uses `cost_cny` + `cost_usd`; (d) same trip's `accommodation.json` uses `cost_eur` only in summary.breakdown. These directories are explicitly out of scope (Won't Have). However: (i) the HTML generator must handle graceful fallback if it ever processes these trips — it should skip or warn on unknown cost schema rather than crash; (ii) a migration guide for these trips should be documented as a future task. The new `plan-validate.py` currency consistency check must not ERROR on legacy `cost_cny`/`cost_usd` fields — it should issue a WARNING and guide towards the single-field model.
