# BA Specification: Harden TimelineView Degenerate Entry Filtering and Optional Item Deduplication

**Request ID**: dev-20260406-020005
**Created**: 2026-04-06T02:00:05Z

## Goal

Harden the filtering and deduplication logic inside `const TimelineView` in
`scripts/generate-html-interactive.py` to eliminate edge cases that can produce
empty, misaligned, or visually broken timeline rows.

## Context

During the current session, `add()` received a degenerate-entry filter and the
entries list received a dedup pass for optional items sharing the same time slot.
These additions need to be verified for correctness and hardened against the
remaining edge cases identified below.

The component lives at line 2535. Key sub-areas are:

- `add()` inline guard (lines 2543-2550)
- `entries.sort()` (line 2577)
- Dedup block (lines 2579-2588)
- `firstH` / `lastH` calculation (lines 2593-2594)
- `top()` pixel placement helper (line 2608)

## Findings from Code Review

### Finding 1: `add()` filter is correct but incomplete

Current guard (lines 2546-2548):
```
if (item?.time?.start && item?.time?.end
    && item.time.start !== '00:00'
    && item.time.start !== item.time.end)
```

Issues:
- `item?.time?.end` is truthy even for `'00:00'`, so `time.end === '00:00'`
  passes. An item with `start='08:00'`, `end='00:00'` is degenerate (midnight
  wraparound sentinel) and should be excluded.
- `'00:00'` check is string-literal; time strings with inconsistent formatting
  (e.g. `'0:00'`) would slip through. `timeToMinutes` already handles split+map
  so all time consumers are safe, but the guard uses string comparison only.
- Zero-duration check `start !== end` catches exact string equality but misses
  numeric equality (e.g. `'09:00'` vs `'9:00'`).

### Finding 2: Dedup key is too coarse (only type, not name)

Current key (line 2584):
```
const key = slot + ':' + e._type;
```

This key collapses ALL optional items of the same type at the same slot into
one entry regardless of what they are. If two genuinely different optional
activities of the same type happen to share a start/end (e.g., two different
optional attractions both at 14:00-16:00), the second is silently dropped even
though it is not a duplicate.

The correct key for "tea option dedup" is slot + type + a stable name
identifier so that identical name/time/type triples collapse but distinct
named alternatives at the same slot do not.

### Finding 3: `firstH` reads `time.start` of the sorted-deduped list but does not guard against non-HH:MM values

Line 2593:
```
const firstH = entriesWithLayout.length ? parseInt(entriesWithLayout[0].time.start) : 8;
```

`parseInt('08:30')` returns `8` correctly. But `parseInt` on a malformed string
(e.g. undefined, null, empty) returns `NaN`, which propagates into `top()` and
produces `NaN` pixel offsets for every entry, making the timeline invisible.
The guard `entriesWithLayout.length ?` only guards against an empty array; a
single entry with a corrupt time field still breaks the whole grid.

### Finding 4: `lastH` uses `entriesWithLayout[last].time.start` not `time.end`

Line 2594:
```
const lastH = entriesWithLayout.length
  ? Math.min(parseInt(entriesWithLayout[entriesWithLayout.length - 1].time.start) + 2, 24)
  : 20;
```

`lastH` is derived from the last entry's `start` + 2 hours, not its actual
`end`. If the last activity is a 3-hour dinner starting at 20:00 (ends 23:00),
`lastH` is capped at `min(22, 24) = 22`. The last hour of the activity falls
below the rendered grid. The correct value is
`max(parseInt(entry.time.end), parseInt(entry.time.start) + 1)` over all
entries, capped at 24.

### Finding 5: `top()` helper is not defensive

Line 2608:
```
const top = (t) => { const [h, m] = t.split(':').map(Number); return (h - firstH) * hH + (m / 60) * hH; };
```

If `t` is undefined or not a valid HH:MM string, `split` throws or returns
`[NaN, NaN]`. Because `add()` now guards upstream, this is mostly safe; but
if any future call path bypasses `add()` and pushes directly to `entries`, the
helper would silently produce `NaN px` positions.

## Requirements (MoSCoW)

### Must Have

- M1: `add()` must also reject entries where `time.end === '00:00'`
- M2: Dedup key must include a stable name identifier (e.g., `name_base` or
  `title`) so that distinct optional items sharing a slot are not collapsed
- M3: `firstH` derivation must fall back to `8` if `parseInt` returns `NaN`
- M4: `lastH` must be computed from the maximum `time.end` across all entries,
  not from the last `time.start` + 2

### Should Have

- S1: Add a numeric zero-duration guard in `add()` using `timeToMinutes` so
  that string format variations (`'9:00'` vs `'09:00'`) do not circumvent the
  check
- S2: `top()` should clamp its return value to `>= 0` to avoid negative pixel
  positions if a stray entry has `start < firstH`

### Could Have

- C1: Log a `console.warn` when `add()` rejects an entry, for debugging
  degenerate data in future sessions

### Won't Have (Non-Goals)

- Changing the visual layout or styles of the timeline
- Altering data-generation logic in the Python layer
- Changing the `computeColumnLayout` algorithm

## Edge Cases & Risks

- Optional items that are genuinely different experiences at the same time slot
  must NOT be deduped (e.g., "Dim Sum" vs "Noodles" both optional at 08:00-09:00)
- Midnight-crossing activities (start > end numerically) are not supported by
  the current renderer; the fix should reject them in `add()` rather than
  attempt wraparound rendering
- `time.end = '00:00'` is used as a sentinel by some YAML generators meaning
  "no time assigned"; the fix correctly treats it as degenerate

## Acceptance Criteria

### AC1: Degenerate end-time rejection
- GIVEN a day entry with `time.start = '09:00'` and `time.end = '00:00'`
- WHEN TimelineView renders
- THEN that entry does not appear in the timeline

### AC2: Zero-duration rejection (numeric)
- GIVEN entries with `time.start = '09:00'` and `time.end = '9:00'` (different string, same value)
- WHEN TimelineView renders
- THEN that entry does not appear in the timeline

### AC3: Distinct optional items at same slot are both shown
- GIVEN two optional entertainment entries with the same `time.start`/`time.end` but different `name_base`
- WHEN TimelineView renders
- THEN both entries appear (only true clones are deduped)

### AC4: `firstH` is always a valid integer
- GIVEN any non-empty `entriesWithLayout`
- WHEN `parseInt(entriesWithLayout[0].time.start)` returns `NaN`
- THEN `firstH` defaults to `8` and the grid renders without NaN pixel offsets

### AC5: Last hour fully visible
- GIVEN the last timeline entry ends at `23:00`
- WHEN TimelineView renders
- THEN the hour grid extends to at least `23`

## Technical Hints

- Affected file: `scripts/generate-html-interactive.py` lines 2543-2594
- `timeToMinutes` (line 2474) is already available in scope; use it for numeric comparison
- The dedup name key should prefer `e.name_base || e.title || e._label` (whichever is present)
- `lastH` fix: `Math.min(Math.max(...deduped.map(e => parseInt(e.time.end) || parseInt(e.time.start) + 1)), 24)`
- Do not change line numbers above 2535 or below 2608 — the fix is contained within the TimelineView function body
