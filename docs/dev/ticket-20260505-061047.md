## Goal

Restore the `/root/rednote-mcp` repository as the single source of truth for the `rednote-mcp` runtime by migrating the substantive feature delta currently orphaned in `/usr/lib/node_modules/rednote-mcp/dist/*` (the `search_notes_light` MCP tool + supporting helpers + telemetry + smart-retry / cover-selector minfix) BACK into the source repo and putting in place the minimum structural guardrails so this anti-pattern (`edit-the-installed-artifact instead of edit-the-source`) cannot recur silently. The user's binding directive is verbatim: `一切修复只能在root/rednote-mcp然后部署到你说的位置 ... 必须两边同步并且root/rednote-mcp是唯一真相来源`.

## Context

On 2026-05-03 the rednote-mcp ecosystem was migrated from a 3-place layout (fork snapshot + patch-farm + installed runtime) to a single-source-of-truth layout: `/root/rednote-mcp/dist/*.js` is the canonical edit target; `/usr/lib/node_modules/rednote-mcp/dist/*` is the deploy target; the patch farm at `/root/travel-planner/infra/rednote-mcp-patches/stealth.patch.d/` is historical. See `/root/rednote-mcp/MIGRATION-20260503.md` for the canonical statement.

In the immediately-prior session, the orchestrator added a new MCP tool `search_notes_light` plus several helper methods (`_waitForNoteDetail`, `_searchNotesEmptyTelemetry`, `_bumpTelemetry`, smart-retry loop, cover-selector multi-fallback) directly to `/usr/lib/node_modules/rednote-mcp/dist/tools/rednoteTools.js` and `/usr/lib/node_modules/rednote-mcp/dist/cli.js`. The patches FUNCTIONALLY work (limit=20: `1/20` success → ~100% success; runtime: `8m24s` → `1m30s`). However the source repo at `/root/rednote-mcp/dist/*` was never updated, so the working code is currently orphaned in the installation path and would be lost on the next deploy / reinstall / fresh-host setup. This is the exact 3-place sync pain the migration was designed to abolish, in a new shape: install-path-as-source-of-truth instead of patch-farm-as-source-of-truth.

A specialist architecture review (2026-05-05T06:18Z, 12 files examined, 8 issues — 4 critical, 2 major, 2 minor) is recorded at `/root/travel-planner/docs/dev/architect-rednote-mcp-source-of-truth-20260505-061800.json`. ## Edge Cases & Risks

- **R1.** **Reconciliation order matters.** If dev runs the deploy script BEFORE writing the installed bytes back into source, the source's stale bytes will overwrite the working installed runtime, losing the `search_notes_light` feature in production. Mitigation: this spec mandates reconciliation order in W5 (reverse-sync FIRST, then commit source, THEN run deploy). The deploy script's M4 step e (sha256 round-trip) catches accidental partial-overwrite as well.
- **R2.** **`rsync --delete` removes `.orig` backup.** The installed copy currently carries `/usr/lib/node_modules/rednote-mcp/dist/tools/rednoteTools.js.orig` (54562 B), a backup left by the orchestrator's editor when it first hand-patched the file. The new deploy script uses `--delete` per architect `arch-prop-1`, which will remove this backup. This is intentional (the file is a hand-edit artifact, not part of the canonical dist tree). Dev should note this in the deploy summary.
- **R3.** **`node --check` may surface latent syntax issues.** The installed `rednoteTools.js` is 132984 B and was hand-edited; if any prior edit left an unbalanced brace it would fail `node --check` here. Mitigation: M3 makes this a hard gate; if it fails, dev MUST fix the syntax in source (and re-deploy) BEFORE the cycle closes — do NOT bypass `node --check`.
- **R4.** **Manifest line wording is informational.** `dist/.stealth-applied-fragments` does not gate runtime loading (per architect `arch-2`). The `T-1-search_notes_light-and-minfix` entry is a documentation choice to surface the addition for future archaeologists; the wording is editable in a follow-up if a stricter naming convention is later adopted (architect `arch-6` proposed `T-*` for tools, `F-*` for non-tool features, `P-*` for stealth — the suggestion is non-binding here).
- **R5.** **Cross-repo consumer (`search_light.py`) is unaffected.** The Python wrapper at `/root/travel-planner/.claude/commands/scripts/rednote/scripts/search_light.py` calls the MCP tool by name string `search_notes_light`. Since this cycle preserves the tool name (verbatim copy of the registration line in cli.js), no consumer-side change is required. The cross-repo contract is documented in `out_of_scope_observations` for visibility but not modified in this cycle.
- **R6.** **`auth/authManager.js` is in sync (no action).** The installed and source `dist/auth/authManager.js` share sha256 `49fed707...` — the prior orchestrator session did not touch it. The deploy script will rsync it as a no-op for that file. Document this in the deploy summary so QA can confirm the no-op.
- **R7.** **Architect `arch-prop-2` and `arch-prop-3` are deliberately deferred.** Skipping them this cycle is a scope decision (per spec-20260503-091826 §5.1) — not an oversight. Deferring is documented in the Could Have list above so the user can authorize them in a later cycle. The minimum-safest-precise floor for THIS cycle is M1–M5 + S1–S3.
- **R8.** **Operator habit risk during the deferred-arch window.** Until `arch-prop-3` (preinstall guard) lands in a future cycle, the install path remains writable by `npm install -g`. The architect names this as the highest-impact residual risk (CLAUDE.md global rule alone has not been sufficient — see this very incident). S3's CLAUDE.md note is the partial mitigation in this cycle; the structural close-out is left to the future cycle that lands C2.
