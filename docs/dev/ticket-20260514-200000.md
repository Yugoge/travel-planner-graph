### Fix 4: Fix gaode subprocess CLI interface in route.py

**Root cause**: `scripts/lib/server/route.py` at `_run_gaode_subprocess` (line 82) calls:
```
python3 <script> --json <payload>
```
The actual gaode routing skill (`routing.py`) uses positional args:
```
python3 routing.py <command> <origin_coords> <destination_coords>
```
where `<command>` is one of `driving`, `transit`, `walking`, `cycling`. Every cache-miss call to `/api/route` fails with a non-zero exit code and returns `{status: "error", reason: "gaode-call-failed"}` instead of route data.

Additionally, `_GAODE_ROUTE_SCRIPT_CANDIDATES` lists `route.py` and `inter-city-route.py` but the actual script is named `routing.py` — this is addressed in Fix 3 above by adding `routing.py` as the first non-env candidate.

**Files to modify**:
- `scripts/lib/server/route.py` — `_run_gaode_subprocess` and `_invoke_gaode` functions

**Implementation**:
The `_invoke_gaode` function currently builds a JSON payload dict and passes it via `--json`. Replace with:
1. Map the `mode` field from the request (`walk`, `taxi`, `driving`, `transit`, `cycling`) to the routing.py command vocabulary (`walking`, `driving`, `transit`, `cycling`). Default unmapped modes to `walking`.
2. Extract `from_coords` and `to_coords` from the trip's POI coordinate data (the existing code may already look up coordinates — preserve that lookup logic).
3. Call: `["python3", str(script), command, from_coords, to_coords]` where coords are `"lon,lat"` strings (Gaode convention: longitude first).
4. Parse the JSON stdout response from routing.py (the response schema from routing.py: `{status, distance_km, duration_min, ...}`).

**Note to dev**: Read `scripts/lib/server/route.py` fully before editing. The existing `_invoke_gaode` likely has coordinate-lookup logic that must be preserved; only replace the subprocess call construction and response parsing, not the coordinate resolution.

**Update test stubs**: `tests/server/test_route_endpoint.py` must be updated so any test that stubs the subprocess output uses the positional-arg format response, not the `--json` format. The existing test `test_unknown_route_returns_unknown_status` (which covers the no-script case) does not need changes; only tests that stub a successful gaode call need updating.

**Acceptance criterion**: `POST /api/route` with valid `from_option_id` and `to_option_id` (cache miss, gaode script present) returns `status != "error"` and `status != "unknown"`. Cache-miss test that stubs the gaode subprocess output produces `status: "ok"`.

### Fix 5: Fix handle_budget trip_total day-scoping bug

**Root cause**: `scripts/lib/server/budget.py` `handle_budget` function. At line 169, `_select_target_days(days, req.get("day"))` filters to only the single day when `day=N` is specified. Lines 170-172 compute `day_entries` from only that filtered set. Line 176 then sums `day_entries` for `trip_total`, producing a `trip_total` that covers only one day instead of all days. The API contract requires `trip_total` to always be the full-trip total regardless of the `day` filter.

**Files to modify**:
- `scripts/lib/server/budget.py` function `handle_budget` (lines ~160-178)
- `tests/server/test_budget_endpoint.py` — add assertion for day-filtered request trip_total

**Implementation** (replace the filtering/compute block):
```python
# Compute ALL days unconditionally for trip_total
all_day_entries = [_compute_day(d) for d in all_days]
trip_total = sum(e["day_total"] for e in all_day_entries)
# Then filter for the response's `days` array
day_n = req.get("day")
if day_n is not None:
    day_entries = [e for e in all_day_entries if e["day"] == day_n]
else:
    day_entries = all_day_entries
```

Note: the variable names `all_days` and `all_day_entries` may differ from what is in the current source — read the function first and adapt accordingly. The fix pattern above uses the redev spec's pseudocode as the canonical shape.

**Test update**: In `tests/server/test_budget_endpoint.py`, add a test (or extend `test_day_filter_returns_single_day`) that asserts:
- `resp["days"]` has length 1 (day filter applied to breakdown)
- `resp["trip_total"]` equals the sum of ALL days (not just the filtered day)
- Use the two-day fixture so the distinction is testable: `trip_total` must equal `day1_total + day2_total` even when `day=1` is requested

**Acceptance criterion**: `POST /api/budget/recompute` with `{"trip_id": "...", "day": 1}` returns `trip_total` equal to the sum of all days. The existing test `test_aggregates_day_costs_correctly` still passes.
