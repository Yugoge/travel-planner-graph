# BA Specification: Restructure Meal Alternatives to Nested Format

**Request ID**: dev-20260406-020001
**Created**: 2026-04-06T02:00:01Z

## Goal

Restructure the `meals.json` data format so that meal alternatives are nested inside each meal type object (`lunch.alternatives`) rather than stored as separate top-level sibling fields (`lunch_alternatives`). This eliminates a schema anti-pattern where related data is fragmented across sibling keys instead of being co-located under their parent.

## Context

The meals agent currently produces two parallel structures per meal type:

- `day.lunch` — the primary meal object (a `meal_item`)
- `day.lunch_alternatives` — a sibling array of backup options

The HTML generator (`generate-html-interactive.py`) reconstructs the relationship at render time by dynamically computing `alt_key = f"{meal_type}_alternatives"` and looking it up in the raw day dict. The schema (`meals.schema.json`) silently permits this via `"additionalProperties": true` on `day_entry`, meaning alternatives are invisible to schema validation entirely.

The target format nests alternatives under the meal object:

```json
"lunch": {
  "primary": { ...meal_item fields... },
  "alternatives": [ ...meal_item array... ]
}
```

This is a pure structural migration — the data content of every field is unchanged.

## Requirements (MoSCoW)

### Must Have
- `meals.json` day entries use `lunch.primary` / `lunch.alternatives` (and breakfast, dinner equivalents) instead of flat `lunch` / `lunch_alternatives`
- `meals.schema.json` updated: `day_entry` properties `breakfast`, `lunch`, `dinner` each become a new `meal_slot` type with `primary: meal_item` and `alternatives: array of meal_item`
- `generate-html-interactive.py` `_merge_day_data()` reads `day_meals[meal_type]["primary"]` and `day_meals[meal_type].get("alternatives", [])` instead of the `alt_key` pattern
- `meals.md` agent prompt updated to emit the new nested format (both in the output example and the format description)
- `sync-agent-data.py` `_sync_meals()` reads `day[meal_type]["primary"]` (currently reads `day[meal_type]` directly as the meal object)
- Existing `data/**/meals.json` files with the old flat format must still render correctly OR be migrated (see Edge Cases)

### Should Have
- `meals.schema.json` `day_entry` marks `additionalProperties: false` after migration so stray `*_alternatives` siblings are caught by validation
- `plan-validate.py` updated if it references `*_alternatives` key pattern (currently no direct reference found — confirm at dev time)
- Migration note added to `meals.md` noting the format change date

### Could Have
- A one-off migration script `scripts/migrate-meals-alternatives.py` that converts existing `data/**/meals.json` files from old to new format
- `load.py` Level 2/3 output adjusted to surface alternatives alongside primary

### Won't Have (Non-Goals)
- Changes to any non-meals agent data format
- Changes to timeline, budget, attractions, entertainment, shopping, transportation schemas
- UI/HTML rendering behavior changes (visual output must be identical before and after)
- Any change to what information is stored — only the structural nesting changes

## Edge Cases and Risks

- **Existing data files**: Six `meals.json` files exist under `data/`. The most recent (`wangfujing-dongdan-beijing-20260405-192905`) uses the old flat format with `lunch_alternatives`. HTML generator must handle both old and new format during transition, OR all existing files must be migrated before the reader code is changed.
- **`save.py` schema gate**: After updating `meals.schema.json`, any attempt to save an old-format file via `save.py` will fail validation. Migration of existing files must happen before or alongside schema tightening.
- **`additionalProperties: false` on `meal_item`**: The `meal_item` def already uses `additionalProperties: false`. The new `meal_slot` wrapper must allow the `primary` + `alternatives` keys explicitly.
- **`_sync_meals()` assumption**: The syncer at line 304 iterates `self._config["meal_types"]` and does `meal = day.get(meal_type)` expecting the result to be a dict with `name_base`. After migration, `day.get(meal_type)` returns `{"primary": {...}, "alternatives": [...]}`, so the syncer must drill into `.get("primary")`.
- **`alt_key` removal**: After migration, the `f"{meal_type}_alternatives"` lookup in `generate-html-interactive.py` lines 581-617 must be replaced with reading from the `primary.alternatives` field. The downstream `merged["meals"][f"{meal_type}_options"]` construction logic is unchanged — only the data source path changes.

## Acceptance Criteria

### AC1: Schema updated and validates new format
- GIVEN a `meals.json` with `lunch: { "primary": {...}, "alternatives": [...] }`
- WHEN `save.py` validates against `meals.schema.json`
- THEN exit code is 0 (no validation errors)

### AC2: Schema rejects old flat format after migration
- GIVEN a `meals.json` with `lunch: {...meal_item...}` and `lunch_alternatives: [...]` as siblings
- WHEN `save.py` validates against updated `meals.schema.json`
- THEN exit code is 1 with a descriptive error identifying the structural mismatch

### AC3: HTML renders identically
- GIVEN a trip with lunch primary and two alternatives in new nested format
- WHEN `generate-html-interactive.py` processes the data
- THEN the HTML output contains the primary option labeled "A" and alternatives labeled "B", "C" in the `_options` array, identical to current behavior

### AC4: Sync agent handles new format
- GIVEN a `meals.json` in new nested format and a `timeline.json` with lunch time entries
- WHEN `sync-agent-data.py` runs
- THEN `lunch.primary.time` is injected from timeline (not `lunch.time`), and no errors appear in sync-report.json

### AC5: Meals agent emits new format
- GIVEN a meals-agent invocation producing lunch with alternatives
- WHEN the agent saves via `save.py`
- THEN `meals.json` contains `lunch.primary` and `lunch.alternatives` (not `lunch_alternatives` at the day level)
