# BA Specification: Semantic Time Constraints for Timeline Agent

**Request ID**: dev-20260406-020004
**Created**: 2026-04-06T02:00:04Z

## Goal

Add semantic time-window constraints to the timeline agent so it schedules meal-typed activities within culturally appropriate time windows, preventing absurd outputs like dinner at 17:10 or afternoon tea at 19:15.

## Context

The timeline agent in `/plan` Step 10 and the agent definition in `.claude/agents/timeline.md` currently optimizes activity order using a nearest-neighbor GPS approach. This approach is purely spatial: it minimises travel distance between locations but has no semantic awareness of what time a "dinner" or "afternoon tea" should occur. The result is that proximity-optimal sequencing can place dinner before 18:00 or afternoon tea well into the evening — both semantically wrong and likely to frustrate travellers.

The timeline agent already carries a soft hint in its validation checklist (`Verify meal times are reasonable: breakfast 7-10am, lunch 12-3pm, dinner 6-10pm`) but this is listed only as a post-hoc validation note, not enforced as a scheduling constraint during timeline construction. The route-optimisation pass does not account for semantic windows at all.

## Requirements (MoSCoW)

### Must Have

- Hard time-window constraints for the five semantic activity categories, enforced during timeline construction (not only at validation):
  - `breakfast`: 07:00–10:00
  - `lunch`: 11:30–14:00
  - `afternoon_tea` / `coffee` / matcha break: 14:30–17:30
  - `dinner`: 18:00–20:30
  - `entertainment` entries that carry `meal_ref` tag: inherit the time window of their referenced meal type
- Activities identified as belonging to one of these categories MUST have their `start_time` clamped to fall within the window even if proximity optimisation would place them outside it
- Activities without any meal semantic (attractions, shopping, intra-city transport) remain scheduled purely by proximity optimisation — no regression to spatial logic
- Both locations where the constraints apply: the timeline agent definition (`.claude/agents/timeline.md`, Step 2 / validation section) and the Step 10 prompt in `.claude/commands/plan.md`

### Should Have

- A clear warning emitted to the `warnings` array when a constraint-clamping occurs, e.g. `"Day 2: Dinner clamped from 17:10 to 18:00 (semantic time window enforcement)"`
- The constraint table documented inline in both files so future maintainers understand the rule without reading this spec

### Could Have

- Configurable time windows per user preference (e.g. early-bird breakfast 06:30–09:00) read from `requirements-skeleton.json` `preferences` field — acceptable to defer to a follow-up iteration

### Won't Have (Non-Goals)

- Changes to route-optimisation logic or GPS/haversine calculation code
- Changes to any agent other than `timeline-agent` (meals, entertainment agents are not being touched)
- Automatic re-scheduling of non-meal activities that become displaced by clamping (displacement warnings are sufficient; full re-schedule is out of scope)
- Any changes to `save.py`, `plan-validate.py`, or validation scripts

## Edge Cases & Risks

- Clamping dinner to 18:00+ may create a gap after the previous activity that would conflict with or duplicate an existing free-time block — the agent should detect and warn but not auto-insert a free-time entry
- If all feasible time slots within a window are occupied, the agent should warn and pick the nearest available slot after the window opens, rather than silently violating the constraint
- The `meal_ref` tag is already required on every meal timeline entry (enforced by `save.py` schema); the new constraint logic must read this existing tag rather than inferring meal type from activity name strings
- entertainment entries with `meal_ref` are relatively rare; the constraint logic must check for the tag before applying a window, not assume all entertainment is unconstrained
- Re-invocation of timeline agent from Step 15 (day-scoped refinement) must also honour the constraints — the constraints live in the agent definition, so this is automatic

## Acceptance Criteria

### AC1: Dinner within window

- GIVEN a day where route optimisation would schedule dinner at 17:10
- WHEN the timeline agent constructs the timeline dictionary
- THEN the dinner entry has `start_time` >= 18:00 and a warning is emitted to `warnings` noting the clamp

### AC2: Afternoon tea within window

- GIVEN a day where route optimisation would schedule an afternoon matcha break at 19:15
- WHEN the timeline agent constructs the timeline dictionary
- THEN the matcha break entry has `start_time` <= 17:30 and a warning is emitted to `warnings` noting the clamp

### AC3: Non-meal activity unaffected

- GIVEN an attraction or shopping location with no `meal_ref`
- WHEN the timeline agent constructs the timeline dictionary
- THEN its start time is determined purely by proximity optimisation with no semantic window applied

### AC4: meal_ref tag drives constraint, not name matching

- GIVEN an entertainment entry with `meal_ref: "dinner"` in its timeline value
- WHEN the timeline agent constructs the timeline dictionary
- THEN it is subject to the dinner time window (18:00–20:30), not scheduled freely

### AC5: Both files updated

- GIVEN the updated codebase
- WHEN a reviewer inspects `.claude/agents/timeline.md` and `.claude/commands/plan.md` Step 10 prompt
- THEN both contain the semantic time constraint table and the enforcement instruction
